# 国际化与语言边界

[English](localization.md) · 简体中文

国际化是整个项目的工程约束，覆盖界面、原生控件、无障碍描述、通知、应用错误、设备状态、Try 预设内容、开发文档和发布材料。目前提供 English、简体中文和「跟随系统」：中文系统使用简体中文，其他系统语言回退到英文。应用内切换语言会以独立的 Android Configuration 重建 Activity，原生控件使用相同语言，不修改设备的系统语言。

纯 Java 的 `:core/text/TextCatalog` 负责不可变的文案和格式规则，`AppText` 负责 Android 偏好与资源上下文。界面通过 `Ui.t`、`Ui.format` 绑定文案，通过 `Ui.explain` 显示应用状态及切换语言前保存的错误。当前 catalog 位于 `android/src/main/assets/i18n/en.json`，采用明确的中文原文 key 与英文译文；错误模板使用完整匹配规则，不做子串替换。

真实用户消息、房间/会话名、识别文本、工具输入输出、文件名、链接、地理位置和设备产品名保持原样。协议字段、标识和内部日志采用稳定的原始值；诊断文字以英文协作，呈现给用户的操作错误通过文案边界翻译。日期、数量和坐标模板使用选定的应用语言，协议数值使用稳定格式。

语言切换会重建可丢弃的 Try 房间，并按所选语言加载预设文字、音频和文件。真实房间的消息与草稿不参与翻译，也不会因此清空。Try 的重建保持与真实网络/数据库的隔离。主题或原生配置重建继续保留当前页面状态；真实房间替换及 Try 重建会推进 viewer generation，丢弃上一代临时通知草稿。

新增文案按以下步骤接入：

1. 将中文原文 key 和英文译文加入 catalog。保留完整句子/模板，使用 `ui.format` 或 `TextCatalog.format` 填入参数，保持参数类型和数量一致。
2. 标签、提示、操作名、无障碍描述使用 `ui.t` 或 `ui.format`；服务/本地通知使用 `AppText.get(context)`；业务与硬件状态在展示时使用 `ui.explain`。新增旧式动态错误时，在 `TextCatalog` 增加完整匹配模板，并补充相关的现有契约用例。
3. 设备适配器不读取 Activity 语言，也不翻译真实设备名称；稳定应用状态由展示层翻译。原生字符串同时维护 `res/values` 英文默认资源、`values-en`、`values-zh`，保持资源名称一致。
4. 执行 `python3 scripts/verify-sources.py`；修改语言解析或格式规则时，再执行 `scripts/test-host.sh`。纯文案改动无需重跑真机回归矩阵。

构建和 CI 的 `scripts/check-localization.py` 检查重复 key、空译文、格式参数、显式 UI 文案、所有生产模块的应用状态（包括扫码和设备适配器），以及原生资源的一致性。直接写入界面的英文文案也要经过国际化调用；品牌/协议标签使用明确的小范围例外。契约覆盖语言回退、不可变作用域、动态错误、用户内容边界、日期/坐标和工具数量。

后续增加语言，需要同步扩展 `TextCatalog` 的解析/catalog/复数规则、设置允许值及选择器、`AppText` 原生 Configuration、Android 资源和 Try 的文字/音频/文件，并增加该语言的回退与格式契约。当前实现支持中英文，还不是通用的 ICU 复数或 RTL 方案；新增语言必须核对语法和布局后再声明支持。

源码标识符、注释、开发工具、发布说明和公开文档以英文为协作语言，README 与主要指南提供中文配套版本。公开截图统一使用英文，旧中文验收记录明确标为历史档案。国际化覆盖应用拥有的文案，不自动翻译真实对话数据。
